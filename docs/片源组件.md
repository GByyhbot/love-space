# 在线片源（一起看 · 片源组件）

> 上游是一台 **Capy 组件聚合器**（NAS 上的 `happy-capy`，`:8788`），它把
> CapyPlayer 的沙箱组件转成了 HTTP。组件数量会继续涨（现在 17 个），所以这份
> 文档的重点不是「怎么调通」，而是**怎么在没人维护文档的情况下继续加、继续改**。

---

## 1. 三层结构

```
上游组件（.js 沙箱脚本，遵循 CapyPlayer 规范）
        │  happy-capy 跑沙箱，摊成 REST
        ▼
/api/v1/providers/<id>/{browse,search}  +  /items/<id>  +  /stream/<签名>
        │  ← 无文档，只能观测
        ▼
┌─────────────────────────────────────────────────────────────┐
│ app/widgets.py   契约层（纯函数，零状态）                    │
│   字段归一化 / 能力判定 / 脏数据过滤                          │
├─────────────────────────────────────────────────────────────┤
│ app/dramas.py    传输层                                      │
│   请求重试 / 缓存 / 健康度 / 覆盖层读取 / HLS 改写与分片代理   │
├─────────────────────────────────────────────────────────────┤
│ settings.drama_overlay   本地整理层                          │
│   别名 / 标签 / 隐藏 / 排序（上游改名不会冲掉）               │
└─────────────────────────────────────────────────────────────┘
        │  本站 /api/dramas/…
        ▼
static/watch.js   片源四层：sources → home → list → detail
```

**规矩**：所有「猜字段」的代码只许出现在 `app/widgets.py`。
别处要新字段，先在那里加一行，再到调用处用——不然半年后又是十几处各猜各的。

## 2. 上游是什么、不是什么

这一条最容易搞错，先钉死：

| 常见误解 | 事实 |
|---|---|
| CapyPlayer 组件是个 REST 服务 | **不是**。组件是公网可访问的 `.js`，宿主在沙箱里 `await` 它的全局函数 |
| 组件有 `capabilities` 字段 | **规范里没有**。能力由「声明了哪些 `modules` / 有没有 `loadDetail`」隐含表达。`capabilities` 是 happy-capy 自己加的**未文档化扩展** |
| 组件有 `categories` 字段 | 规范里也没有。分类是 `type:"category"` 的模块返回 `WidgetSystemCategory[]`，被这层壳压成了 `categories[]` |
| 有 search / playback 专用端点 | 规范里没有。搜索就是数据源函数，播放是 `loadDetail` 返回的 `videoUrl`/`playSources` |

所以我们的策略是：**按 CapyPlayer 规范的字段表做归一化**（那是唯一有权威定义的
部分），把 happy-capy 的扩展（`capabilities`、`categories`）当提示用，不当契约用。

参考：<https://capyplayer.feifeiduck.cn/zh/dev/widget/widgetdev>

## 3. 实测契约（`docs/capy-contract.json`）

2026-11-05 探针抓的实际形状，17 个组件：

| 层级 | 字段 |
|---|---|
| provider | `id` `title` `version` `capabilities[]` `categories[{id,title}]` |
| 列表页 | `items[]` `page` `pageCount` `total` |
| 条目 | `id` `title` `mediaType` `posterUrl` `description` `remark` |
| 详情 | `id` `title` `mediaType` `posterUrl` `description` `seasonCount` `episodeCount` `seasons[]`　（红果另有 `currentSeason` `currentEpisode` `currentEpisodeName` `videoUrl` `playUrl` `url` `playerType`） |
| 剧集 | `id` `title` `episodeNumber` + **`streamUrl`** 或 **`mediaUrl`+`resolveUrl`**（MissAV 还多一个 `rawStreamUrl`，目前不用） |

**剧集地址有两种流派**，这是最容易踩的一条：

| 流派 | 组件（实测） | 取地址方式 |
|---|---|---|
| 直给 | 69ck, hanime1, hongguo, jable, lissav, mitao, ptt, rouav… | `streamUrl` 直接用 |
| 二次解析 | 51chigua, hlbdy, huangdou, huangju, yeguo | 拿 `resolveUrl` 再请求一次，取 `videoUrl` |

契约层对两种都认（`_URL_KEYS` / `_RESOLVE_KEYS`），不用按组件分支。

### 3.1 两份清单：`/providers` 报 17 个，`/components/catalog` 报 20 个

上游有**两份**清单，说的不是同一件事 —— 这是「我装了 20 个组件，你只接进 17 个」
的全部原因：

| 接口 | 内容 |
|---|---|
| `GET /api/v1/providers` | 只列实现了**通用 provider 契约**的组件（能 browse / detail / play） |
| `GET /api/v1/components/catalog` | 列这台机器上**装着的全部**组件（含内建） |

差集固定是这三个（2026-11-05 本机实测）：

| 组件 | `backendType` | `artifacts` | `backendCapabilities` |
|---|---|---|---|
| `bilibili` 哔哩哔哩 | `builtin` | 只有 `widget.js` | `widget:universal@1` |
| `huangguo` 黄果短剧 | `builtin` | 只有 `widget.js` | `huangguo:cover@1` `huangguo:routes@1` `widget:access-bootstrap@1` |
| `missav` MissAV | `builtin` | 只有 `widget.js` | `discovery:missav@1` `missav:playlist@1` `missav:prepare@1` `missav:subtitles@1` `video:proxy@1` `widget:access-bootstrap@1` |

**判据只有一条**：`backendCapabilities` 里有没有 `provider:<id>@1`。

- 有 → 后端有 `provider.so`，`/api/v1/providers/<id>/…` 能用；
- 没有 → 安装包里**只有 `widget.js`、没有 `provider.so`**，抓取逻辑跑在手机端的
  Widget 沙箱里，服务端一侧没有任何实现。

翻遍宿主 `openapi.json` 的 **63 条路由**也没有「跑任意外挂组件」的入口，最接近的是
`/api/v1/stream/bili/*`，那只是流转发、不出列表。所以这三个**不是漏接，是接不了**：

| 组件 | 为什么接不了 | 有没有别的路 |
|---|---|---|
| `bilibili` | 通用组件运行时 + DASH，播放链路跟现有 HLS 完全不同 | 无 |
| `huangguo` | 正文抓取在 widget 里，服务端只给线路（`/huangguo/routes`）和封面（`/huangguo/cover`） | 无 |
| `missav` | 内建通道只有 `/missav/rankings`（仅编号）和 `/missav/detail?code=`（0.7–2.5s/条），凑一页要逐条请求 | **有**：`missav-official` 是同一个站点的通用实现，封面标题齐全 |

处理方式：这三个**照样显示**（组件列表追加在通用组件之后，`builtin: true`、
`usable: false`、`alt` 指向替代组件），卡片用虚线边 + 「内建」徽章区分，
点进去是说明而不是片单。**不静默吞掉**——静默少 3 个只会让人以为这边坏了；
也不给假入口——点一次报一次 404 更糟。

计数行因此写「共 20 个组件，17 个能用」，两个数都给出来。

## 4. 字段映射表（规范 → 我们的键）

顺序即优先级，实现在 `app/widgets.py`：

| 语义 | 读取顺序 |
|---|---|
| 条目标题 | `title` → `name` |
| 条目 ID | `id` → `mediaId` |
| 海报 | `posterUrl` → `poster_url` → `poster` → `posterPath` → `coverUrl` |
| 简介 | `description` → `overview` → `desc` |
| 时长/集数提示 | `remark` → `note` |
| 媒体类型 | `mediaType` → `media_type`（白名单 `movie/tv/series/show`） |
| 剧集号 | `episodeNumber` → `episode_number` → `episode` → `ep` |
| 剧集地址 | `streamUrl` → `videoUrl` → `video_url` → `url` → `path` → `link` → `mediaUrl` → `playSources[默认线路]` |
| 二次解析地址 | `resolveUrl` → `resolve_url` → `resolve` |

**详情容器也认三种**（都有实测或规范依据）：

1. `seasons[].episodes[]` —— 主流
2. 顶层 `episodeItems[]` / `episodes[]` —— 规范里的扁平写法
3. 顶层 `videoUrl`/`playUrl`/`url` —— **movie 类只有一个地址**（以前这里直接 404）

第 3 种要小心：红果的 tv 详情**同时**有 `seasons` 和顶层 `videoUrl`（值是第 1 集），
所以「先看 seasons，没有再退到顶层」的顺序不能反，否则每部剧都会多出一集。

## 5. 加一个新组件要做什么

**通常什么都不用做。** 上游 `/api/v1/providers` 里出现新 id，它就自动出现在
「片源组件」页。要检查的只有三件事：

1. `GET /api/drama-sources?refresh=1` 能看到它（`online=true`）
2. 点进去能翻分类（能不能 `browse`）
3. 第一条能取详情且 `episodes` 非空（`/api/drama-sources/diagnostics?probe=1`）

三项都过 = 不用改代码。有一项不过，按第 6 节定位。

**前提是它在 `/api/v1/providers` 里。** 只在 `/api/v1/components/catalog` 里、
`backendCapabilities` 没有 `provider:<id>@1` 的（内建组件），无论怎么装都接不上，
见第 3.1 节 —— 那种情况不用排查，排查也没用。

如果**新字段**出现（比如这次发现的 `rawStreamUrl`），处理顺序是：

1. `python scripts/capy_probe.py --write --diff` → 看字段增删
2. 判断它属于哪张表：条目 / 详情 / 剧集 / 分页
3. 在 `app/widgets.py` 对应位置加一个候选键（**加在末尾**，别抢现有的优先级）
4. 在 `tests/test_widgets.py` 补一条字面量 JSON 用例

## 6. 上游变了怎么发现

上游没有状态页、没有 changelog，所以做了两个自证工具：

### 6.1 契约探针（看字段有没有变）

```bash
python scripts/capy_probe.py --write --diff     # 抓一遍并和上次快照对比
python scripts/capy_probe.py --diff             # 只比文件，不发请求
```

输出形如：

```
  + episode_fields: rawStreamUrl
  - 组件消失: hsex
```

`docs/capy-contract.json` 是快照，字段增删才是契约变更；标题、条目内容变了不算。

### 6.2 体检报告（看现在能不能用）

管理页的「整理」旁没有入口，直接敲接口（或以后加按钮）：

```bash
curl -b cookie "http://<host>/api/drama-sources/diagnostics?probe=1"
```

每个组件给四段：`browse`（分类翻不翻得动）、`detail`、`episodes`、`playable`，
外加 `needs_resolve`（这个源每集要不要多解析一次）和 `ms`（总耗时）。
返回里还带 `net`（第 7 节的网络模式），一颗接口就能看清「该谁去连 + 现在通没通」。

⚠️ **比较慢**：4 路并发跑 17 个组件，实测 15s 上下（以前串行要 60s+）。
只在排查时用，别做成定时任务。不带 `probe=1` 时只回内存里的健康度，不碰上游。

### 6.3 健康度

`catalog()` 每个组件带 `health: {ok, error, at, ms}`（最近一次请求的结果）。
组件卡上看到「连不上」就是它。只保留最后一次——上游的可用性是分钟级的，
留历史只会误导。

## 7. 网络模式（`/api/v1/diagnostics`）

同一个组件「该由谁去连源站」，决定了它挂了以后该怎么救。上游把这件事做成了
四档，CapyPlayer 首页卡片上原样展示；我们也照搬同一套说法，主人在两个界面看到
的话术才一致。

| `network_mode` | 中文 | 含义 | 挂了怎么办 |
|---|---|---|---|
| `direct` | 服务器直连 | 容器服务器直连源站，无需代理 | 查 NAS 出网（DNS / 上游链路） |
| `mobile` | 手机端直连 | 播放器手机客户端直接拉流，不占服务器流量 | **不要**给服务端挂代理，先在手机上试播 |
| `proxy_suggested` | 建议海外代理 | 受海外源站网络限制 | 给它挂局部代理 |
| `proxy_configured` | 海外代理已配置 | 已经配了代理 | 确认代理在容器里可达，再重启组件让 worker 重读配置 |

⚠️ `mobile` 是唯一一个「服务端检查失败 **不代表**播不了」的情况。代码里
`wsNetBad()` 专门把它排除在异常之外，卡片上显示「待手机验证」而不是「连不上」。
把它和服务端直连的源混为一谈，就会对着一个能用的源让人去配代理。

### 7.1 数据从哪来

只有一个来源：`GET /api/v1/diagnostics` 的 `results[<id>]`。
`/api/v1/providers` 不提供（`?verbose=1` / `?include=network` / `?detail=1` 全被忽略）。

```jsonc
"results": {
  "dsd": {
    "network_mode": "direct", "network_text": "服务器直连",
    "status": "failed",                    // passed | warning | failed
    "server_check_role": "required_metadata",
    "checks": { "basic": {...}, "server": {...}, "client": {...}, "playback": {...} },
    "impact_hint": "服务器获取内容存在异常…",
    "diagnostic_text": "…问题定位: 未能访问 https://www.dsd.com.se/",
    "historical": true                     // 这份结果是缓存的（上游窗口 600 秒）
  }
}
```

**只 GET，不 POST。** `POST /api/v1/diagnostics` 会让上游真的去访问每个源站
（本机 9 个组件 8 秒，带超时的源更久）。打开一次组件列表就产生这种副作用是不可
接受的，所以触发留给显式命令：

```bash
python scripts/capy_probe.py --diag --write --diff    # 先跑全量诊断，再抓快照
```

### 7.2 我们下发什么、不下发什么

`app/widgets.py:network()` 是唯一入口，只取白名单字段：

| 下发 | 不下发 |
|---|---|
| `mode` / `label` / `short` | `diagnostic_text`（含「问题定位」，带源站域名） |
| `status`、`checks.{basic,server,client,playback}` 的**状态** | `checks.*.label` / `checks.*.text`（上游的措辞） |
| `role`、`stale` | `target`、`started_at`、`finished_at` |

另外所有说明文字都过一遍 `scrub()`：`scheme://…`、IPv4[:端口]、域名、`user@host`、
`password=…` 一律替成 `***`。**代理 IP 和密码永远不会出现在界面上** ——
这既是主人明确要求，也是因为那张卡片是给人看的，不是给排障看的。

### 7.3 缺项是常态

上游只诊断它自己排的那一批：本机 **17 个组件里只覆盖 9 个**。所以：

- 没进 `results` 的组件 `net` 是 `{}`，卡片上不画徽章（空徽章比没有更让人困惑）；
- 组件页计数行会写「共 17 个组件，9 个有网络模式」，说明为什么不是张张都有；
- 前端所有判断都要写成 `net.mode === 'mobile'` 这种**正向匹配**，不能写
  `!== 'direct'` —— 未知值必须落到「没有意见」那一支。

`network_mode` 为空串（内建源 `hongguo` / `huangguo` / `missav` 就是这样）时同样
不画徽章。上游将来加新模式时，`mode` 留空、原文进 `unknown` 字段，**绝不冒充**
已知的四种之一 —— 猜错的标签比没有标签更误导人。

### 7.4 与 `health` 的关系

两者并列、互不覆盖：

- `health` = **我们**刚才那次请求成没成（`browse` / `item` 的真实结果）
- `net` = **上游**说这个源该由谁去连（语义，不是状态）

一个 `mobile` 组件可以 `health.ok === false` 而完全正常 —— 因为真正拉流的是手机。
反过来 `net.status === 'passed'` 也不保证我们这边一定通（上游测的是它的视角）。

### 7.5 本机实测：**只有帝果（`dsd`）需要海外代理**

17 个组件里，只有帝果一家是海外源、必须挂代理才能连；其余都是国内直连。

**但上游不会告诉你这件事。** 查过全部相关接口：

- `GET /api/v1/providers/<id>/manifest` 只有 `id` `title` `version` `capabilities` `categories`
- `GET /api/v1/components` 只有 `runtimeMode` / `lifecycleState` / `artifacts` / `backendType`
- `diagnostics` 的 `network_mode` 在本机只会出现 `direct` 和空串，**从不出现** `proxy_suggested` / `proxy_configured`

所以「要代理」是纯本地知识，落在覆盖层的 `proxy` 布尔上（第 8 节）：
主人在「整理」里给帝果勾一次「需代理」，之后卡片显示「需代理」徽章、
连不上时也按代理那条给建议 —— 而不是让人去查 NAS 出网。

⚠️ 别指望用 `network_mode` 判断要不要代理：它在本机对帝果也报 `direct`。

### 7.6 两个实测案例，别把它们混为一谈

| 现象 | `net` | `health` | 真实原因 | 卡片怎么说 |
|---|---|---|---|---|
| `dsd` 帝果 | `direct` / `failed` | 失败 | 容器 `/config/config.toml` 里有 `[providers.dsd] proxy`，但 worker 日志仍是 `Errno 101 Network is unreachable` **直连** —— 配置没被采纳，上游也因此仍把它标成「服务器直连」 | 「需代理」徽章 + 让你检查 `[providers.dsd]` 的 proxy 并重启组件 |
| `yeguo` 野果 | `direct` / `passed` | 失败（20s 504） | 上游自检那一刻是通的，只是这个源本身极慢，我们等不到 | 「上游自检通过、我们超时，过会儿再试」 |

`yeguo` 这条尤其重要：`status === 'passed'` 却失败时，让人去「查 NAS 出网」是错的
方向 —— 网络是通的，是慢。所以 `watchNetAdvice()` 里 `status === 'passed'` 的分支
**排在模式分支之前**；而本地「需代理」标记又排在所有模式分支之前。

## 8. 本地整理（`drama_overlay`）

上游负责**发现**，本地负责**整理**。两者分表存，是因为上游随时会改标题、增删组件；
把显示名混进同一张表，上游改名就会把主人的命名冲掉。

```http
PUT /api/drama-sources/overlay
{"key": "capy:dsd", "alias": "帝果", "tag": "影视", "order": 1, "hidden": false, "proxy": true}
```

| 字段 | 作用 |
|---|---|
| `alias` | 显示名，覆盖上游 `title`。上游原名保留在 `title` 字段里 |
| `tag` | 分组标签。**只要有一个组件带标签，组件页就按标签分组**，否则按服务分组 |
| `proxy` | 「这个组件需要海外代理」。**上游没有这个信息**（manifest 里没这字段），只能本地标。标过之后卡片显示「需代理」，连不上时按代理给建议 |
| `order` | 组内排序，小的在前，未设置的排在后面 |
| `hidden` | 从组件页收起（可用「显示已隐藏的 N 个」展开）。**不影响接口可用性** |

点「整理」按钮就是这套接口的图形入口。缺省值表示「不动」，`alias: ""` 表示恢复原名。

## 9. 排障

| 现象 | 先查 |
|---|---|
| 组件卡显示「上游异常」 | `diagnostics?probe=1` 看是 browse 还是 detail 挂；多半是上游 502/504 |
| 点进去分类全空 | 该组件第一个分类本来就没内容；换个分类看 |
| 选集页「这个内容还没有可播的剧集」 | 详情里既没有剧集也没有顶层地址。跑探针看 `detail_fields` / `episode_fields` 有没有新名字 |
| 播放一直转圈 | `/source/<集>` 判断是 mp4 还是 hls；hls 要过 `rewrite_playlist`，看是不是 302 到源站后相对分片拼错了 |
| 「换一批」点不动 | 到 `pageCount` 了。上游红果一个分类 1413 页，别以为是 bug |
| 组件页找不到某个源 | 被 `hidden` 收起了；点「显示已隐藏的 N 个」 |
| 上游改名了本地还是旧名 | 检查 `drama_overlay` 里有没有这个键的 `alias` |
| 组件卡没有网络模式徽章 | 上游诊断快照没覆盖它（17 个里只有 9 个）。跑 `capy_probe.py --diag` 刷新 |
| 配了代理还是连不上 | 上游 `[providers.<id>] proxy` 只对部分运行模式生效；worker 是独立进程，改配置后要重启该组件让 worker 重读 |

## 10. 已知限制

1. **列表级的直链不支持**。规范允许条目直接带 `type:"url"` + `videoUrl` 跳过详情页，
   但现在的链路是「列表 → 详情 → 选集 → 流」，没有这条捷径。**目前 17 个组件
   没有这么写的**，真出现了再加。
2. **`capabilities` 只影响界面**。它明确说没有 `search` 时隐藏搜索按钮；
   其他情况一律按「支持」处理——宁可多一个入口，也别把功能藏起来。
3. **多季只按集号排**。`seasons` 会被摊平，集号跨季会重复（第 1 季第 1 集 / 第 2 季
   第 1 集都是 `n=1`）。现在没有多季的源，UI 也只有一排集号；真遇到再改成分季。
4. **体检改成 4 路并发了**。`diagnose_many()` 用信号量卡住并发数，17 个组件从
   60s+ 降到 15s 上下。再往上加并发会让上游更慢（它本来就是台爬虫机器）。
5. **`mobile` 组件仍然走服务端转发**。上游说它「该由手机直连」，但我们这条链路
   一律经 `/api/drama-stream` 转发 —— 要真做客户端直拉，得把带签名的直链下发到
   前端（约 24 小时后失效）并放开 CSP 的 `media-src`，代价远大于收益。
   所以 `mobile` 目前只影响**提示文案**（不让人去挂服务端代理），不影响播放路径。
6. **`max-age` 相关的缓存语义**见 `README` / `main.py` 中间件注释，不在本文范围。
7. **内建组件（bilibili / huangguo / missav）接不了**。它们的抓取跑在手机端的
   Widget 沙箱里，服务端没有实现，宿主也没提供「跑外挂组件」的接口。界面上照样
   列出来并标「内建」，但不给入口（详见第 3.1 节）。要真正支持 bilibili，等于从零
   写一个 bilibili 数据源 + DASH 播放链路，不属于「接组件」的范畴。
