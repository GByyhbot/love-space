# 在线片源（一起看 · 片源组件）

> 上游是一台 **Capy 组件聚合器**（NAS 上的 `happy-capy`，`:8788`），它把
> CapyPlayer 的沙箱组件转成了 HTTP。组件数量会继续涨（现在 17 个），所以这份
> 文档的重点不是「怎么调通」，而是**怎么在没人维护文档的情况下继续加、继续改**。

---

## 1. 三层结构

```
上游组件（.js 沙箱脚本，遵循 CapyPlayer 规范）
        │  happy-capy 跑沙箱，摊成 REST
        ▼
/api/v1/providers/<id>/{browse,search}  +  /items/<id>  +  /stream/<签名>
        │  ← 无文档，只能观测
        ▼
┌─────────────────────────────────────────────────────────────┐
│ app/widgets.py   契约层（纯函数，零状态）                    │
│   字段归一化 / 能力判定 / 脏数据过滤                          │
├─────────────────────────────────────────────────────────────┤
│ app/dramas.py    传输层                                      │
│   请求重试 / 缓存 / 健康度 / 覆盖层读取 / HLS 改写与分片代理   │
├─────────────────────────────────────────────────────────────┤
│ settings.drama_overlay   本地整理层                          │
│   别名 / 标签 / 隐藏 / 排序（上游改名不会冲掉）               │
└─────────────────────────────────────────────────────────────┘
        │  本站 /api/dramas/…
        ▼
static/watch.js   片源四层：sources → home → list → detail
```

**规矩**：所有「猜字段」的代码只许出现在 `app/widgets.py`。
别处要新字段，先在那里加一行，再到调用处用——不然半年后又是十几处各猜各的。

## 2. 上游是什么、不是什么

这一条最容易搞错，先钉死：

| 常见误解 | 事实 |
|---|---|
| CapyPlayer 组件是个 REST 服务 | **不是**。组件是公网可访问的 `.js`，宿主在沙箱里 `await` 它的全局函数 |
| 组件有 `capabilities` 字段 | **规范里没有**。能力由「声明了哪些 `modules` / 有没有 `loadDetail`」隐含表达。`capabilities` 是 happy-capy 自己加的**未文档化扩展** |
| 组件有 `categories` 字段 | 规范里也没有。分类是 `type:"category"` 的模块返回 `WidgetSystemCategory[]`，被这层壳压成了 `categories[]` |
| 有 search / playback 专用端点 | 规范里没有。搜索就是数据源函数，播放是 `loadDetail` 返回的 `videoUrl`/`playSources` |

所以我们的策略是：**按 CapyPlayer 规范的字段表做归一化**（那是唯一有权威定义的
部分），把 happy-capy 的扩展（`capabilities`、`categories`）当提示用，不当契约用。

参考：<https://capyplayer.feifeiduck.cn/zh/dev/widget/widgetdev>

## 3. 实测契约（`docs/capy-contract.json`）

2026-11-05 探针抓的实际形状，17 个组件：

| 层级 | 字段 |
|---|---|
| provider | `id` `title` `version` `capabilities[]` `categories[{id,title}]` |
| 列表页 | `items[]` `page` `pageCount` `total` |
| 条目 | `id` `title` `mediaType` `posterUrl` `description` `remark` |
| 详情 | `id` `title` `mediaType` `posterUrl` `description` `seasonCount` `episodeCount` `seasons[]`　（红果另有 `currentSeason` `currentEpisode` `currentEpisodeName` `videoUrl` `playUrl` `url` `playerType`） |
| 剧集 | `id` `title` `episodeNumber` + **`streamUrl`** 或 **`mediaUrl`+`resolveUrl`**（MissAV 还多一个 `rawStreamUrl`，目前不用） |

**剧集地址有两种流派**，这是最容易踩的一条：

| 流派 | 组件（实测） | 取地址方式 |
|---|---|---|
| 直给 | 69ck, hanime1, hongguo, jable, lissav, mitao, ptt, rouav… | `streamUrl` 直接用 |
| 二次解析 | 51chigua, hlbdy, huangdou, huangju, yeguo | 拿 `resolveUrl` 再请求一次，取 `videoUrl` |

契约层对两种都认（`_URL_KEYS` / `_RESOLVE_KEYS`），不用按组件分支。

## 4. 字段映射表（规范 → 我们的键）

顺序即优先级，实现在 `app/widgets.py`：

| 语义 | 读取顺序 |
|---|---|
| 条目标题 | `title` → `name` |
| 条目 ID | `id` → `mediaId` |
| 海报 | `posterUrl` → `poster_url` → `poster` → `posterPath` → `coverUrl` |
| 简介 | `description` → `overview` → `desc` |
| 时长/集数提示 | `remark` → `note` |
| 媒体类型 | `mediaType` → `media_type`（白名单 `movie/tv/series/show`） |
| 剧集号 | `episodeNumber` → `episode_number` → `episode` → `ep` |
| 剧集地址 | `streamUrl` → `videoUrl` → `video_url` → `url` → `path` → `link` → `mediaUrl` → `playSources[默认线路]` |
| 二次解析地址 | `resolveUrl` → `resolve_url` → `resolve` |

**详情容器也认三种**（都有实测或规范依据）：

1. `seasons[].episodes[]` —— 主流
2. 顶层 `episodeItems[]` / `episodes[]` —— 规范里的扁平写法
3. 顶层 `videoUrl`/`playUrl`/`url` —— **movie 类只有一个地址**（以前这里直接 404）

第 3 种要小心：红果的 tv 详情**同时**有 `seasons` 和顶层 `videoUrl`（值是第 1 集），
所以「先看 seasons，没有再退到顶层」的顺序不能反，否则每部剧都会多出一集。

## 5. 加一个新组件要做什么

**通常什么都不用做。** 上游 `/api/v1/providers` 里出现新 id，它就自动出现在
「片源组件」页。要检查的只有三件事：

1. `GET /api/drama-sources?refresh=1` 能看到它（`online=true`）
2. 点进去能翻分类（能不能 `browse`）
3. 第一条能取详情且 `episodes` 非空（`/api/drama-sources/diagnostics?probe=1`）

三项都过 = 不用改代码。有一项不过，按第 6 节定位。

如果**新字段**出现（比如这次发现的 `rawStreamUrl`），处理顺序是：

1. `python scripts/capy_probe.py --write --diff` → 看字段增删
2. 判断它属于哪张表：条目 / 详情 / 剧集 / 分页
3. 在 `app/widgets.py` 对应位置加一个候选键（**加在末尾**，别抢现有的优先级）
4. 在 `tests/test_widgets.py` 补一条字面量 JSON 用例

## 6. 上游变了怎么发现

上游没有状态页、没有 changelog，所以做了两个自证工具：

### 6.1 契约探针（看字段有没有变）

```bash
python scripts/capy_probe.py --write --diff     # 抓一遍并和上次快照对比
python scripts/capy_probe.py --diff             # 只比文件，不发请求
```

输出形如：

```
  + episode_fields: rawStreamUrl
  - 组件消失: hsex
```

`docs/capy-contract.json` 是快照，字段增删才是契约变更；标题、条目内容变了不算。

### 6.2 体检报告（看现在能不能用）

管理页的「整理」旁没有入口，直接敲接口（或以后加按钮）：

```bash
curl -b cookie "http://<host>/api/drama-sources/diagnostics?probe=1"
```

每个组件给四段：`browse`（分类翻不翻得动）、`detail`、`episodes`、`playable`，
外加 `needs_resolve`（这个源每集要不要多解析一次）和 `ms`（总耗时）。

⚠️ **很慢**：17 个组件 × 2 次上游请求，实测 60s 上下，个别源单次就要 11s。
只在排查时用，别做成定时任务。不带 `probe=1` 时只回内存里的健康度，不碰上游。

### 6.3 健康度

`catalog()` 每个组件带 `health: {ok, error, at, ms}`（最近一次请求的结果）。
组件卡上看到「上游异常」就是它。只保留最后一次——上游的可用性是分钟级的，
留历史只会误导。

## 7. 本地整理（`drama_overlay`）

上游负责**发现**，本地负责**整理**。两者分表存，是因为上游随时会改标题、增删组件；
把显示名混进同一张表，上游改名就会把主人的命名冲掉。

```http
PUT /api/drama-sources/overlay
{"key": "capy:hongguo", "alias": "红果", "tag": "短剧", "order": 1, "hidden": false}
```

| 字段 | 作用 |
|---|---|
| `alias` | 显示名，覆盖上游 `title`。上游原名保留在 `title` 字段里 |
| `tag` | 分组标签。**只要有一个组件带标签，组件页就按标签分组**，否则按服务分组 |
| `order` | 组内排序，小的在前，未设置的排在后面 |
| `hidden` | 从组件页收起（可用「显示已隐藏的 N 个」展开）。**不影响接口可用性** |

点「整理」按钮就是这套接口的图形入口。缺省值表示「不动」，`alias: ""` 表示恢复原名。

## 8. 排障

| 现象 | 先查 |
|---|---|
| 组件卡显示「上游异常」 | `diagnostics?probe=1` 看是 browse 还是 detail 挂；多半是上游 502/504 |
| 点进去分类全空 | 该组件第一个分类本来就没内容；换个分类看 |
| 选集页「这个内容还没有可播的剧集」 | 详情里既没有剧集也没有顶层地址。跑探针看 `detail_fields` / `episode_fields` 有没有新名字 |
| 播放一直转圈 | `/source/<集>` 判断是 mp4 还是 hls；hls 要过 `rewrite_playlist`，看是不是 302 到源站后相对分片拼错了 |
| 「换一批」点不动 | 到 `pageCount` 了。上游红果一个分类 1413 页，别以为是 bug |
| 组件页找不到某个源 | 被 `hidden` 收起了；点「显示已隐藏的 N 个」 |
| 上游改名了本地还是旧名 | 检查 `drama_overlay` 里有没有这个键的 `alias` |

## 9. 已知限制

1. **列表级的直链不支持**。规范允许条目直接带 `type:"url"` + `videoUrl` 跳过详情页，
   但现在的链路是「列表 → 详情 → 选集 → 流」，没有这条捷径。**目前 17 个组件
   没有这么写的**，真出现了再加。
2. **`capabilities` 只影响界面**。它明确说没有 `search` 时隐藏搜索按钮；
   其他情况一律按「支持」处理——宁可多一个入口，也别把功能藏起来。
3. **多季只按集号排**。`seasons` 会被摊平，集号跨季会重复（第 1 季第 1 集 / 第 2 季
   第 1 集都是 `n=1`）。现在没有多季的源，UI 也只有一排集号；真遇到再改成分季。
4. **体检是串行的**。17 个组件依次探，慢。要提速得加并发闸门，暂时不值得。
5. **`max-age` 相关的缓存语义**见 `README` / `main.py` 中间件注释，不在本文范围。
