# love-space · 定位守护功能计划（对标市面情侣自动报备软件）

起草：2026-11-22；修订：同日按机主要求对齐市面同类产品功能全集（Lookus、LinkUp、Findus、心轨、陪伴喔）。状态：**计划稿，待机主圈定决策点后按期立项**。范围：仅 Android（双机均为小米，iOS 无限期搁置）；数据全量落在自有 NAS，不经任何第三方云。

## 一、为什么 love-space 做这件事有底子

| 所需能力 | 现有资产 | 结论 |
|---|---|---|
| 后台常驻采集 | 2.4.5 前台服务（specialUse）全天保活 SSE，已过小米白名单实战 | 定位/状态采集挂靠此服务，不新起保活体系 |
| 实时下发 | SSE `/api/events` 现成通道 | 位置更新、报备事件走 SSE，不用轮询 |
| 通知触达 | 本地通知（前台服务链）+ 企业微信机器人兜底（机主实际依赖后者） | 关键报备双通道：App 通知为主，可加企业微信 |
| 鉴权与写入 | Cookie `love_session` + `X-Love-Space: 1` 写门禁 | 新接口沿用，不新造 |
| 双向对等 | 空间本身只有两个人、同一套账号体系 | 天然双向，不需要市面产品的匹配码绑定流程 |

与市面产品的本质差异（优势）：对方数据在厂商云端且核心功能收费，本方案位置、轨迹、使用记录全部只存 NAS，公网线路只做传输，全功能自有。

## 三、技术方案要点

### 3.1 定位采集（App，挂靠现有前台服务）
- **关键前提（开源实证，见第七节）**：国产机无 GMS 时 FusedLocationProvider 回调永不触发——Flutter 的 geolocator 等插件默认走 Fused，直接用会全军覆没。定位路线二选一（决策点 2）：
  - **路线 A · 高德定位 SDK**：输出即 GCJ-02，与高德地图同系、无偏移；需注册高德 Key（免费额度够用），多一层 SDK 合规与包体。
  - **路线 B · 原生 LocationManager + 端上坐标转换**：GPS/NETWORK/PASSIVE 三 provider（couple-tracker 已在国产机验证可行），输出 WGS-84，端上做 WGS-84→GCJ-02 转换（成熟公开算法）后再上报；零 Key、零第三方 SDK。
- **自适应采样**（省电核心，参数吸收开源实证值）：硬件级位移触发 minDistance≈25 m（系统判断、零 CPU 唤醒）；静止确认（连续 3 次无位移）后降为 5 min 间隔心跳（附带电量/网络/充电/Wi-Fi 状态）；PASSIVE provider 复用其他 App 的定位结果零耗电补点；上报批量聚合（攒满 5 条或距上次超 3 min 才 POST，本地缓存上限约 50 条，失败重试）。不做秒级连续定位。
- 前台服务类型注意：现有服务为 specialUse 类型，加入定位采集后需按 Android 14+ 规范核对 FGS type 声明与后台定位权限（ACCESS_BACKGROUND_LOCATION 需单独引导授予「始终允许」），此点列入一期第 0 步实测（小米机真机验证服务不被系统杀、定位不断档）。
- 断网/离线：本地队列暂存，恢复后补传（标记补传点，轨迹不断线）。

### 3.2 后端（NAS，独立小表，不动既有契约）
- `peer_location_latest`：每人一行最新状态（经纬度、精度、电量、充电、网络、Wi-Fi、更新时间）。
- `peer_location_points`：轨迹点（user、ts、lat、lng、acc、speed），按保留期滚动清理（见决策点 1）。
- `peer_places`：围栏点（名称、经纬度、半径）。
- `peer_events`：报备事件流（类型、ts、摘要、是否已推送），动态流页与推送同源于此表。
- `peer_usage_daily`：使用报告日汇总（屏幕时长、解锁数、Top App 时长 JSON），端上每小时增量上报。
- 接口：`POST /api/peer/location`（批量补传）、`POST /api/peer/events`（批量）、`GET /api/peer/status`、`GET /api/peer/track?date=`、`GET /api/peer/events?date=`、`POST /api/peer/sos`、围栏与开关读写；全部 Cookie 鉴权 + 写接口 `X-Love-Space: 1`；位置更新与关键报备经 SSE 以新事件类型下发（不改既有事件语义）。围栏到离事件同时落通知中心（非 chat 类，按既有口径计入铃铛，与 2026-11-20 裁决不冲突）。
- 存储估算：行进 30 s/点、活跃移动 4 h/日 ≈ 500 点 + 静止心跳 ≈ 每人每日 ≤700 点；15 天 × 2 人 ≈ 2 万点；事件流每人每日约百条量级。SQLite 无压力。

### 3.3 报备事件实现口径（Android 无 GMS 的现实，先说清近似边界）
市面产品的报备形态是**两层**，本计划照此设计（见决策点 7）：
- **动态流**：全部事件进对方的「报备动态」时间线，随时翻看，不逐条打扰；
- **关键推送**：仅勾选的关键事件（到家、离开家、上下车、低电量、关定位、紧急）推通知（+可选企业微信）。

逐条口径：
- **到达/离开预设地点**：地理围栏精确判定，围栏边缘加迟滞（进/出各需持续满足约 2 min）防抖动连发。推送层。
- **上车/下车**：国内小米机无 GMS 活动识别，**用速度 + 位移状态机近似**：静止 → 持续移动（速度与位移双条件满足约 1 min）判「出发」；移动 → 静止满约 4 min 判「到达」。精度弱于系统活动识别（步行短距离可能不触发、堵车静止可能误判到达），页内与设置中明示近似口径。推送层（可关）。
- **任意地点停留**：静止满约 10 min 生成停留事件（地点取停留中心点 + 高德逆地理文字），入动态流；停留结束补记时长。
- **解锁手机**：屏幕/UsageStats 事件近似计数，入动态流，不推送。
- **打开 App**：UsageStats 前台事件流水，入动态流；指定 App（机主自选清单）可单独设「打开即推」或「连续使用超 N 分钟推」。
- **Wi-Fi/网络**：连通性回调 + SSID（定位权限已覆盖 SSID 读取），入动态流；连上从未见过的 Wi-Fi 可选推送。
- **充电三态**：系统广播精确——开始充电/充满入动态流；低电量（阈值可设，默认 20%）推送，同阈值去重、充电恢复重置。
- **关定位**：定位服务开关变化监听，推送（敏感事件，防失联口径）。
- **开机**：BOOT_COMPLETED 后补报一条，入动态流。
- **通话**：仅电话状态监听——「开始通话/通话结束（时长 X 分钟）」入动态流；**不读通话记录库、不报号码**（号码与历史统计属通话记录裁决范围，默认不做）。
- **晚睡**：规则事件（如 23:30 后仍在持续用机）入动态流 + 可选推送；入睡/起床时间为报告页推断值，注明近似。

### 3.4 地图与轨迹页（App）
- 地图实现二选一（与决策点 2 联动）：高德地图 Flutter 插件，或 **WebView + 离线 Leaflet + 高德瓦片**（couple-tracker 验证的免 SDK 路线：无 Key、无合规流程，瓦片走高德公开服务；Flutter 侧嵌 WebView 页即可，轨迹折线 Leaflet 原生支持）。路线 B 定位 + Leaflet 瓦片组合可实现全程零第三方 Key。
- 地图页：双方位置标记 + 距离 + 状态卡（电量/网络/更新时间/运动状态），对方移动时 SSE 增量刷新标记，不整页重拉；支持街道/卫星切换（市面标配）。
- 轨迹页：日期选择 + 时间轴滑块回放，折线 + 起止点 + 停留点（带停留时长），出行方式按速度分段标注（步行/乘车近似）。
- 报备动态页：按日时间线（事件图标 + 时间 + 摘要），与轨迹页可互相跳转（点出行事件跳当日轨迹）。
- 入口位置：一期建议放「我们」页卡片 + 首页今日双格旁的状态条（最终以机主看稿为准，属 UI 验收范畴）。

### 3.5 开关与对等（产品原则，先于功能写死）
- 定位共享、轨迹可见、报备动态、使用报告四类**各自独立开关**；任一方关闭，对方端明确显示「对方已关闭 XX 共享」，不许显示空白/假故障（市面产品的透明原则）。
- 每类报备的推送开关按事件类型逐项可调（动态流恒全量，推送按勾选）。
- 紧急强提醒可被接收方单独关闭；关闭动作对方可见。
- 位置与事件数据保留期到期**自动滚动删除**（与媒体回收站「不自动删」的裁决是两类数据，不互相套用），保留期在设置页可见。

### 3.6 耗电验收线
- 一期真机实测：开启定位共享后，单日增量耗电 ≤ 约 5%（同机对比基线），超线先调采样参数（位移阈值/心跳间隔）再谈上线。二期报备全开后复测一次。

## 四、分期计划

### 一期 · 定位核心（建议段号 2.8.0）
第 0 步：高德 Key 与 SDK 接入实测、FGS 类型与后台定位权限在小米真机跑通、采样策略耗电摸底、双机 24 h 连续性观察。
主体：采集与上报（含离线补传）、后端 peer 表与接口、地图页（位置+状态卡+距离+在线状态）、轨迹页（按日回放、停留点）、共享开关与关闭态展示。
验收：双机真机对开——位置刷新延迟、轨迹连续性、断网补传、耗电线、关闭开关后对方端展示，五项机主实测。

### 二期 · 自动报备中心
围栏点管理与到离报备、上下车状态机、停留事件、设备事件组（解锁/Wi-Fi/充电/关定位/开机/通话状态）、报备动态页、关键推送分层与逐项开关、紧急强提醒（全屏 + 最大音量，勿扰豁免引导）。
验收：真实进出围栏触发、上下车近似口径实测（步行/乘车/堵车三场景）、静音下强提醒穿透、事件去重与迟滞（围栏边缘、堵车静止不误报）、动态流完整性抽查。

### 三期 · 使用报告与杂项
UsageStats 接入与授权引导页、日汇总上报、报告页（屏幕时长/解锁/Top App/流水/入睡起床推断）、晚睡与久玩提醒规则；可选顺手项：实时语音播放、水印相机。
验收：与系统设置屏幕时间口径抽查对齐（允许近似差异并页内注明）、未授权时引导与降级展示。
通话记录统计是否纳入三期，机主单独裁决（默认不纳入）。

## 五、风险与边界（先说清）
- **MIUI 保活**：定位服务被系统杀即断档，靠现有前台服务 + 白名单已大幅缓解，但一期第 0 步必须双机各跑 24 h 连续性观察后再进主体。
- **定位漂移**：室内/地库 GPS 漂移会污染轨迹，端上按精度半径过滤（acc 过大不落点）+ 静止判定抑制漂移点。
- **近似口径**：上下车、出行方式、解锁数、入睡起床均为近似实现（无 GMS/系统级 API 的现实），与市面宣传口径有差距，全部在页内/设置中明示，不冒充精确。
- **权限被拒降级**：任一权限未授，对应功能显示未开启态，不许崩、不许反复弹窗催授。
- **隐私边界**：本功能仅限两人空间内部；位置/事件数据不进备份导出明文包（默认不导出，如后续要做另行裁决）。

## 六、待机主决策点（圈定后即可按期出提示词）
1. 轨迹保留期：7 天 / **15 天（建议）** / 30 天（市面多为 7–15 天，LinkUp 宣称 30 天）。
2. 定位与地图路线：**路线 A 高德 SDK 全家桶** / **路线 B 原生定位 + 端上坐标转换 + Leaflet 高德瓦片（零 Key，开源实证可行）**。两条都可落地，A 省事在坐标同系，B 胜在零依赖；一期第 0 步可各做一个最小验证再定。
3. 关键推送通道：仅 App 通知 / **关键事件（到家、紧急）加企业微信（建议）** / 全部推送类事件加企业微信。
4. 紧急强提醒形态：**全屏 + 最大音量响铃约 30 s（建议）** / 仅全屏不响铃。
5. 通话记录统计：**不做（建议）** / 三期可选纳入（本计划二期的通话报备仅状态与时长、不含号码，不在此决策内）。
6. 一期入口形态：先按「我们」页卡片 + 首页状态条出稿，真机看稿再调（默认建议，可直接拍板）。
7. 报备形态：**动态流全量 + 关键事件推送（市面形态，建议）** / 全部事件逐条推送（会很吵，不建议）。

## 七、开源参考研读：Anrylin/couple-tracker（2026-11-22 研读）

机主发现的同类开源项目（原生 Kotlin Android + Supabase，活跃开发中，版本 0.209）。克隆研读结论：

- **完成度只到本计划一期的一半**：已实现实时定位、地图双点（WebView Leaflet + 高德瓦片）、App 前台切换流水、设备状态上报（电量/充电/网络/Wi-Fi/亮屏）、配对码、开机自启；**未实现**轨迹回放、统计页、SOS、围栏与全部报备事件（均为其自列 Todo）。二期报备中心无参考价值，一、三期有。
- **可借鉴的实证机制**（已吸收进 3.1/3.3/3.4）：①国产机必须原生 LocationManager、Fused 永不回调；②省电参数——minDistance 25 m 硬件位移触发、静止 3 次确认降 5 min、PASSIVE 零耗电补点、批量 5 条/3 min 上报；③设备状态「事件即报 + 节流 + 亮屏/息屏双节奏」采集结构；④UsageStats 游标法查事件（防固定窗口漏报/重复）；⑤FGS 三类型声明（location|dataSync|specialUse）与 Android 14 启动前权限预检；⑥地图免 SDK 路线（Leaflet 离线包 + 高德瓦片）。
- **不可借鉴**：其后端 RLS 全关、anon key 硬编码、密码自存 crypt——安全口径是反面教材，与 love-space 自有后端 + Cookie 鉴权无关，不受影响。
- **授权红线**：该仓库**无 LICENSE 文件**，默认版权保留——可研读借鉴设计与参数，**代码不可直接复制**进 love-space，实现须自研。
